Digital Twin Assisted Network Slicing for 6G

SSL, TGNN and MARL inside a Digital Twin. Status as of 12 Oct 2026, with the points to settle with sir; updated 16 Oct with our answers to his review comments.

Update, 16 Oct: sir's four comments

  1. Which datasets do the papers use? Of the 16 papers we reviewed, 8 generate their own data with a simulator, emulator or testbed, only one uses Milan, and none uses a single dataset that joins traffic, topology, actions and SLA outcomes.
  2. Is there unified data? No. We checked the 10 datasets we hold and searched for more. The closest (B5G transport traces, single-cell O-RAN traces) have no per-cell allocation actions or SLA outcomes.
  3. So we created it. Real Milan traffic on the real 100 x 100 grid, latency calibrated on the 6G RAN telemetry dataset (mean SLA-vs-load gap 0.021), load-coupled interference and injected incidents. The Digital Twin dataset has 393.6 million rows and 122 columns: a 400-cell year with 6 what-if scenarios, and the full 10,000-cell city for all 62 recorded days.
  4. Why MARL and not a single agent? Same reward, same training budget, held-out days, 3 seeds. MARL holds 0.76–0.77 from 9 to 100 cells with one shared 19k-parameter actor. A tuned single agent falls from 0.41 to 0.27, below equal split, as its network grows to 604k parameters. MARL matches the expert rules; the expert rules fed our TGNN forecast are still better (0.79–0.84).

Prediction helps, so far through the expert controller. The TGNN forecast lifts the expert rules by about 0.05 reward at every network size, but as an extra MARL input it did not help (0.765 vs 0.778). A forecaster retrained on patches of the whole city beats persistence on all 10,000 cells (eMBB +19%), where the one trained on 100 central cells failed. All numbers: results dashboard.

What we tell sir today

  • All four datasets are ready, and the pipeline runs end to end: SSL, TGNN, MARL, Digital Twin gate.
  • SSL is trained on 1.2M flows: accuracy 0.766, Macro-F1 0.708 on held-out data. It matches raw features and beats random embeddings.
  • The TGNN forecasts Milan traffic and beats a "predict the last value" baseline by about 14% on a full day. Feeding raw features instead of SSL embeddings scores the same, so the SSL stage adds nothing on this task yet.
  • MADDPG scores 0.447 on held-out samples against 0.372 for the heuristic, with a simple reward because B5G has no latency or loss data.
  • We found and fixed two evaluation bugs (split leakage on NIDD, wrong-slice scoring on B5G).
  • Simu5G is installed and a real 5G run works. We want his view on the plan below.

Our approach

  1. Self-supervised learningLearn compact traffic representations from unlabelled telemetry by hiding some features and reconstructing them from the rest. Output: a fixed 64-D embedding per node per time step.
  2. Temporal GNNGraphSAGE aggregates neighbours at each step, a GRU carries state over time. Predicts the next step's throughput, latency and load.
  3. Multi-agent RLMADDPG, one agent per node and slice. Each chooses a share of resources across eMBB, URLLC and mMTC, scored by a reward built from QoS, utilization and reconfiguration cost.
  4. Digital Twin gateA candidate allocation is tested in the twin first. It is approved or rejected before anything would touch the real network.

The idea: existing Digital Twin and RL slicing work reacts to what the network already did. Putting a prediction stage (stages 1 and 2) in front of the controller lets it act on what is about to happen. No single public dataset has topology, traffic, and allocation actions with rewards together, so each stage is built on the dataset that fits it and the stages are joined through fixed interfaces (the 64-D embedding, and a predicted-demand record).

Datasets and what each is used for

DatasetWhat it isUsed for
5G-NIDD 1.2M labelled 5G network flows (benign and attack), with protocol fields. Train and evaluate the SSL encoder. Labels are used only to test how useful the embeddings are.
Telecom Italia Milan 62 days of SMS, call and internet traffic on a 100 × 100 grid of cells, every 10 minutes. SSL on traffic features, then the TGNN forecast (400-cell block, real grid adjacency).
NeversNet5G Vehicular 5G NR telemetry from Nevers: 716 UE files, about 27 GB, 19 gNodeBs, produced by a Simu5G + SUMO run. Real UE-to-gNodeB topology (695 nodes), telemetry replay, and the source configuration for our Simu5G scenario.
B5G slicing 7,984 network samples with topology and per-slice (eMBB, URLLC, mMTC) flows and a QoS deviation value, delta. The environment for the MARL stage: observations, rewards and the train / validate / test split.

How we check ourselves: every result uses a held-out split (stratified for NIDD, chronological for Milan, separate sample blocks for MARL) and is compared against a simple baseline, since a model that cannot beat the baseline has not shown value yet.

Two bugs found and fixed. The NIDD file is ordered in same-label blocks, so a sequential split put 99.88% of one class in the test set (about 1% accuracy). The B5G environment scored most rewards against the wrong slice, which invalidated our earlier MADDPG numbers. Both are fixed, with a regression test for the second.

How we proceed

  1. Make SSL earn its place. Raw inputs match the SSL embeddings on the Milan forecast. Next we try an SSL encoder that sees neighbouring cells and earlier intervals, and test longer forecast horizons and more days.
  2. Connect the stages with real data. The Digital Twin loop still uses placeholder embeddings for B5G. We will train an SSL encoder on B5G's own slice features and feed it through the TGNN.
  3. Try a joint SSL representation across NIDD and Milan, which is the gap our literature review points at, and test whether it transfers.
  4. Move from replay to a live simulator. Wire our 19-gNodeB Simu5G scenario in. A simulator produces the latency and packet-loss telemetry that B5G lacks, which is what lets the reward use more than one term and lets the twin approve actions.
  5. Calibrate SLA thresholds once we have the source paper's definition of delta.

End review: the outcome we show (tentative)

  1. A working Digital Twin demo. Real data goes in, the twin produces embeddings, a traffic forecast and a slice allocation, then approves or rejects it. Shown live, not only as slides.
  2. The main claim, tested. Our contribution is that predicting before allocating helps. We have not tested that yet. The end review needs an ablation: MARL with the TGNN's predicted demand against MARL without it, and the TGNN with SSL embeddings against raw features (run once: no gain, so this needs a better SSL encoder).
  3. One results table for every module against its baseline on held-out data: SSL F1, TGNN error against persistence, MARL reward against the heuristic.
  4. Simulator evidence, if the Simu5G scenario gets wired in. The twin then sees real latency and packet loss and decides on real SLA values. If it does not get wired in, we say clearly that the evidence is offline replay.
  5. Limitations and reproducibility. What did not work, what the data cannot support, and a repository anyone can rerun.

Items 2 and 4 are the ones that decide whether the project's claim is supported. They depend on the TGNN beating its baseline and on the simulator integration, so we should agree with sir which of the two is the priority.
