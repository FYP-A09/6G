\section{Introduction}
The prototype is \emph{Slice Twin}, a browser-based monitor that shows how different controllers divide the bandwidth of each cell between eMBB, URLLC and mMTC over one day of real Milan traffic. It turns the environment of Chapter~\ref{chap.4} and the experiments of Chapters~\ref{chap.7} and~\ref{chap.8} into something that can be inspected interactively. The source is in \texttt{app/slice\_twin} of the project repository, and the monitor, a results dashboard and a project brief are published at \texttt{https://fyp-a09.github.io/6G/}.

\section{Purpose and Design}
Slice Twin makes the behaviour of the controllers visible, shows how incidents affect each slice, and compares forecast-based allocation with simpler allocation on the same data.

\paragraph{Data shown.}
One held-out day is replayed, Wednesday 6 November 2013, which was not used to train the forecaster (the forecaster excludes days 5 and 6 of the data for this reason). The traffic is real Telecom Italia Milan data \cite{barlacchi2015}. Scripted incidents are injected so that the controllers have something to react to: an mMTC storm, an interference spike, a cell outage, a backhaul degradation, a flash crowd and a URLLC burst on the central block. The city view adds four more: a firmware push in the north-west, wide-area interference in the east, storm damage in the south and a crowd at San Siro. All incidents are labelled and described in the interface. They are scripted for demonstration and are not real events.

\paragraph{Interaction model.}
The interface is inspired by Cisco Packet Tracer. In Realtime mode the day plays continuously at a selected speed. In Simulation mode playback stops at each new event. An event list shows every incident with its time, cells and description, and a timeline marks the incidents and lets the user jump to any time.

\section{Views and Controllers}
\label{sec:slice-views}
\paragraph{Block view.} The 100 central cells ($10\times10$) are drawn as rings whose segments show the split of each cell between the three slices, with moving packets for served traffic. Selecting a cell opens an inspector with its demand, allocation, latency against target and SLA status for each slice.

\paragraph{City view.} All 10{,}000 cells are drawn as a map coloured by real traffic, by load or by SLA misses, with landmarks (Duomo, Milano Centrale, San Siro, Linate airport, Navigli, Citt\`a Studi) and the active incidents. Selecting a cell compares the three controllers on it over the day, and a cell of the central block can be opened in the block view. City-wide series show the bandwidth given to each slice and the fraction of cells meeting each SLA, with an option to show the gain over the Reactive controller.

\paragraph{Controllers.} Three controllers run in the same environment (Chapter~\ref{chap.4}).
\begin{itemize}
	\item \textbf{Static:} an equal split of each cell's capacity that never changes.
	\item \textbf{Reactive:} the expert rule, which gives URLLC and mMTC enough capacity to stay under their SLA-safe utilisation and the rest to eMBB, using the current demand.
	\item \textbf{Predictive:} the same rule fed with the TGNN forecast of the next ten minutes (the city-trained forecaster of Chapter~\ref{chap.6} in the city view).
\end{itemize}
These are the controllers of Section~\ref{sec:city-controllers}, so the monitor agrees with Table~\ref{tab:city-controllers}. On the central block (Table~\ref{tab:block-controllers}) the Predictive controller is better than Reactive, and an oracle that knows the true next demand would be better still. Over the whole city the Static split scores highest.

\section{Technical Notes}
\label{sec:slice-tech}
\paragraph{Technology and data flow.}
Slice Twin is a static web application with no server-side code. All calculations are done beforehand, and the browser (HTML, CSS and JavaScript) only reads the prepared files and draws the views (Figure~\ref{fig:slice-flow}).
\begin{figure}[htbp]
	\centering
	\small
	\fbox{\parbox{0.92\textwidth}{\centering
	Milan traffic $\rightarrow$ unified environment $\rightarrow$ three controllers with incidents and forecast (Python, offline)\\
	$\downarrow$\\
	\texttt{data.json} (block), \texttt{city.json} and \texttt{city.bin.gz} (city)\\
	$\downarrow$\\
	Browser reads the files and draws the views and charts}}
	\caption{Data flow of the Slice Twin monitor}
	\label{fig:slice-flow}
\end{figure}
The files are produced by \texttt{showcase.py} for the block view and \texttt{showcase\_city.py} for the city view, both in \texttt{src/unified}. The city data is stored compactly. For every interval and cell, one byte holds the log-scaled demand, and for each controller one byte holds the load (scaled by 250) and one byte holds flags: bits 0 to 2 for each slice meeting its SLA, bit 3 for an event and bit 4 for an outage. The compressed binary file is a few megabytes, which lets the browser handle 10{,}000 cells over 144 intervals and three controllers.

\paragraph{How to run it.}
From the repository root, \texttt{python -m http.server 8765 --directory app/slice\_twin} serves the monitor at \texttt{http://localhost:8765}. To regenerate the data, run \texttt{showcase.py}, then \texttt{forecast\_city\_v2.py} once to train the city forecaster, then \texttt{showcase\_city.py}; the Milan files must be on the project drive. A GitHub Actions workflow publishes the monitor, the results dashboard and the project brief to GitHub Pages whenever the site or monitor folders change.

\section{Contribution to the Project}
\label{sec:slice-contrib}
The Slice Twin monitor is the working product of the project, supported by the code, the unified environment and the dataset in the repository. It also serves as a demonstration tool. A viewer can see that the predictive controller helps in the dense centre, that the static split holds up better on quiet outer cells, and how each incident affects each slice. Its limits are those of its data: it shows one held-out day with scripted incidents, and it does not control a live or simulated network. It is a monitoring and comparison tool, not a deployed controller.
